1System Component Overview

One FastAPI process serves a static frontend, a RAG chatbot, an HR candidate matcher, and a LangGraph agent — all sharing one SQLite pair, one Chroma collection, and one Groq LLM client factory.

3RAG Query Pipeline (Hybrid Retrieval)

The actual retrieval path traced from rag_service.py::stream_query_rag_service() — not an assumed textbook RAG flow.

flowchart LR
    Q["User Question
+ chat_history"] --> COND{"History present?"}
    COND -->|"yes"| CND["Condense chain
Groq LLM → standalone question"]
    COND -->|"no"| EMBQ
    CND --> EMBQ["Embed question
(implicit, MiniLM)"]
    EMBQ --> DENSE["Dense search
Chroma k=15"]
    EMBQ --> BM25Q["BM25 search
k=15"]
    DENSE --> ENS["EnsembleRetriever
weighted fusion 0.5 / 0.5"]
    BM25Q --> ENS
    ENS --> RRK["FlashRank rerank
→ top 4 (RERANKER_TOP_N)"]
    RRK --> CIT["Build citations
{source, page, snippet}"]
    RRK --> CTX["Assemble context"]
    CTX --> PR["rag_chain prompt
context + history + question"]
    PR --> LLM2["Groq LLM (stream)"]
    LLM2 --> SSE["SSE: citations → token* → end"]
k=15 per sub-retriever weights 0.5 / 0.5 rerank top_n=4 no similarity threshold configured RERANKER_MODEL setting unused by FlashRank

4HR Candidate Matching Pipeline

Reuses the same chunker + Chroma collection as general RAG, disambiguated by candidate_id metadata. Scoring math is deterministic; only the evidence extraction step is LLM-driven.

flowchart TB
    JD["Job Description upload"] --> JDP["jd_parser_service
Groq LLM → structured JSON"]
    JDP --> NORM1["skill_normalizer
static ~90-entry map"]
    NORM1 --> JOBROW[("hr_jobs.jd_parsed_json")]

    RES["Resume batch upload"] --> RP["resume_parser_service
extract → chunk → tag candidate_id"]
    RP --> VEC2[("Chroma — same shared collection")]

    TRIGGER["POST /analyze (sequential per candidate)"] --> EV["Evidence retrieval
vector search filtered by candidate_id"]
    VEC2 --> EV
    EV --> FR2["FlashRank rerank → top 6 passages"]
    FR2 --> LLMX["Groq LLM: extract skills / experience /
education / evidence quotes (JSON)"]
    JOBROW --> LLMX
    LLMX --> GUARD["Hallucination guard:
missing-skills recomputed as set-difference
vs ground-truth JD skills (LLM output discarded)"]
    GUARD --> SCORE["scoring_engine.calculate_candidate_score()
deterministic weighted formula"]
    SCORE --> PERSIST[("hr_candidate_scores / _profiles / _evidence")]
    PERSIST --> LB["GET /leaderboard
SQL join + Python rank"]
Score ComponentWeightLogic
Required skills40%set-intersection ratio vs JD required skills
Experience25%100 if meets min years, else linear ratio
Project relevance15%keyword bucket (high/medium/low) from LLM text
Preferred skills10%set-intersection ratio vs JD preferred skills
Education5%boolean flag from LLM extraction
"Domain fit"5%mislabeled reuses experience-fit string, JD's actual domain field is never read
Fit thresholds: ≥80 Strong Fit · ≥60 Moderate Fit · <60 Weak Fit. Chunk page numbers for resumes are synthetic (idx // 3 + 1), not real PDF pages.

6LangGraph Agent Flow

route_by_intent always returns the same node — actual branching happens via if/elif inside tool_execution_node, not graph conditional edges.

flowchart LR
    START((START)) --> AN["analyze_query_node
Groq intent classification (temp=0.0)"]
    AN --> RT["route_by_intent
(always → tool_execution_node)"]
    RT --> TE{"tool_execution_node
if/elif on intent"}
    TE -->|"PLAYBOOK_QA / GENERAL"| T1["search_hr_knowledge
→ calls RAG query pipeline"]
    TE -->|"CANDIDATE_MATCHING"| T2["match_candidates"]
    TE -->|"CANDIDATE_DETAILS"| T3["get_candidate_details / evidence"]
    TE -->|"INTERVIEW_GEN"| T4["generate_interview_questions"]
    TE -->|"EMAIL_GEN"| T5["draft_candidate_email"]
    TE -->|"HR_ACTION"| T6["send_candidate_email
(human approval gate)"]
    T1 --> RG["response_generation_node
(passthrough, no further LLM step)"]
    T2 --> RG
    T3 --> RG
    T4 --> RG
    T5 --> RG
    T6 -->|"approval pending"| HOLD["MemorySaver checkpoint
awaiting /agent/approve or /reject"]
    HOLD --> RG
    RG --> END((END))
MemorySaver is in-memory only — a server restart during a pending human-approval step silently loses that state.

No per-user vector isolation: every authenticated user can retrieve every document in the shared Chroma collection. No foreign keys anywhere in the SQLite schema — relationships are convention-only.
